# 代码审查标准与流程（Code Review 机制）

> 适用仓库：`xhs-viral-digest`（极光AIGC 社媒中控，Open Core 架构）
> 配套模板：`docs/code_review/checklist.md`（审查时复制勾选）
> 状态：2026-09-04 建立 · 第一版

---

## 0. 一句话说人话

代码审查 = **每次改动想进主库之前，先让「机器 + 第二双眼睛」各过一遍**，把明显的问题（写错、漏边界、把账号密码带进仓库、把 demo 当真实数据跑）在合入前拦住，而不是等上线/交接后才炸出来。

- 机器（CI）：跑得快、铁面无私，拦「格式/能不能跑/红线」——**硬门禁，不过不放行**。
- 人/AI（审查者）：看得深，拦「逻辑对不对、以后好不好改、有没有踩项目潜规则」——**软门禁，合并前必走**。
- 为什么之前质量参差：不是大家不认真，是**没有统一标准**——审什么、怎么给结论、红线有哪些，全靠临场。这份文档把「标准」和「流程」写死，谁审都一个套路。

## 1. 两级审查模型

```
改动完成
   │
   ▼
【L1 机器闸 · 硬门禁】        ← CI 全自动，不过 → 打回
   ├─ commitlint   提交信息符合 Conventional Commits
   ├─ run_loop.py doctor --ci   开箱即死检查
   └─ pytest tests/ -q          回归测试
   │
   ▼
【L2 审查闸 · 软门禁】        ← 合并 main 前必走（人 或 AI 预审+人终审）
   ├─ 按 checklist.md 逐维审查（正确性/安全/可维护/性能/测试）
   ├─ 项目红线一票否决检查
   └─ 结论：Approve ✅ / Request Changes 🔴
   │
   ▼
修复 → 回归（重跑 L1）→ 合入 main → 记 CHANGELOG
```

### 改动分级（决定 L2 审多严）

| 级别 | 改动类型 | 审查要求 |
|---|---|---|
| 🟢 轻 | docs、注释、示例、CI 配置 | L1 绿即可；L2 只扫红线 |
| 🟡 中 | pipeline/ 功能改动、bugfix、新脚本 | L2 全 checklist；改动路径须有测试或手工验证记录 |
| 🔴 重 | `core/` 架构改动、数据链路（爬取→分析→飞书）、红线相关 | L2 全 checklist + 双人确认（owner 终审）；须补回归测试 |

## 2. 审查标准（审什么）

按五个技术维度 + 本项目红线。每个问题用统一格式标注，见第 4 节。

### 2.1 正确性（能不能用）
- 改动是否真的解决目标问题？边界条件（空数据、重复 note_id、缺列、BOM、全角字符）处理了吗？
- 幂等性：脚本重复跑会不会重复写/翻倍？批量写入断点续跑是否安全？
- 长任务是否被塞进了请求/交互路径？（应独立进程跑）
- 错误路径：失败时有没有可读报错、会不会吞异常假装成功？

### 2.2 安全与隐私（本项目最高优先级）
- 🔴 凭证是否泄漏：`.env` / token / cookie / 账号 id 是否可能进公开仓库？`print`、日志、错误消息里有没有敏感信息？
- 🔴 输入边界：网络/CSV/文件来的数据是否在校验后才用？URL 是否清洗（`?xsec_token=` 截断、全角竖线标签过滤）？
- 文件路径：读写在项目内还是漫游到个人目录？删除操作是否有护栏？

### 2.3 可维护性（6 个月后还看得懂吗）
- 分层：控制器（HTTP/入口）→ 服务（业务）→ 仓储（数据）是否各司其职？入口处有没有掺业务、业务里有没有掺 HTTP？
- 命名是否表意；魔法数字/字符串是否该提常量；重复代码是否该抽函数。
- 注释写「为什么」，不写「是什么」。
- 项目特有坑：Windows 子进程中文参数必须列表传参（GBK 乱码）、CSV 用 `utf-8-sig` 读（BOM）、日期毫秒 int / 多选数组 / 值过 `norm_value`（若动飞书链路）。

### 2.4 性能（有明显瓶颈才拦）
- N+1 查询、循环里发网络请求、批量接口连发触发限流（飞书写接口连发偶发 Exit 1）。
- 大数据集是否无谓全量加载/重复 IO。

### 2.5 测试（改过的路要有证据）
- 改动路径有没有测试覆盖？bugfix 是否带了防回归用例？
- 手工验证路径是否在 PR/提交说明里写清楚（怎么复现、预期什么）。

### 2.6 项目红线（一票否决，任犯一条直接 Request Changes）
1. **demo 红线**：demo CSV（`*_demo*`）只作列格式参考，禁止作为 run 输入、禁止复制进 csv 目录当数据跑通闭环。主路唯一：装依赖 → 装爬虫 → 爬真实数据 → run。（代码层 `core/local_runner.find_csvs` 已拦截，改动不得绕过）
2. **Open Core 边界**：含账号信息的私有适配器（`sync_to_feishu.py` / `run_competitor_crawl.py` / `crawl_self.py` / `parse_self_notes.py` / `xhs_self_notes/` 等）只留本地，`.gitignore` 覆盖，永不进公开仓库；新增私有脚本必须同步加进 `.gitignore`。
3. **品牌风格锁语义**：`accounts/<id>/brand.json` 的 `_locked` / `_visual_locked` / `_copy_locked` 锁定后不得被 `--refresh` 静默覆盖；`--account` 必填、缺号报错，绝不默认值兜底串号。
4. **账号先行主路**：任何改动不得破坏「爬自己账号 → 现象分析 → 主诉 → 调研 → 风格框架 → 打分卡 → 爬爆款验证 → 选题池 → 简报 → 成稿」的路径骨架（内容可变，路径与效果不变）。
5. **业务主键**：飞书侧禁止改默认主键名；业务主键走普通字段 + upsert。

## 3. 审查流程（怎么走）

### 3.1 触发
- 所有合入 `main` 的改动（含 AI 直接改本地后提交）都必须过 L1；L2 至少「作者自检 checklist + 红线自查」。
- 🔴 级改动：必须显式 L2 审查（人工终审），不因「AI 写的」或「改动小」豁免。

### 3.2 角色
| 角色 | 谁 | 职责 |
|---|---|---|
| 作者 | 开发者 / AI | 提交前自检 checklist、写清改动说明与测试计划 |
| 审查者 | 第二人 / AI 预审 | 按 checklist 审、给结论、教学式反馈 |
| 终审人（owner） | 项目 owner / 全栈开发 | 🔴 级与红线相关改动的最终拍板；合入 |

> AI 审查定位：可做 L1.5「预审」，高效扫五维 + 红线；**终审决策必须是人**——AI 看不到行业潜规则与账号策略（历史上 demo 红线、账号先行就是人拍板后固化的）。

### 3.3 结论格式（统一，团队通用）
- 🔴 **Blocker（必须改）**：红线违规 / 正确性错误 / 数据丢失风险 / 凭证泄漏。
- 🟡 **Suggestion（建议改）**：缺校验 / 命名混乱 / 缺测试 / 明显低效。
- 💭 **Nit（可选）**：风格 / 文档小补 / 备选方案。

每条结论三件套：**位置 + 为什么（风险）+ 怎么改（建议）**。只报「有问题」不给位置的 review 是无效 review。

### 3.4 问题编号闭环（沿用 P# 体系）
发现的问题按严重级编号登记，修复后回归、归档进 CHANGELOG：
1. 登记：`P0-拦路` / `P1-崩溃` / `P2-严重` / `P3-一般` / `P4-轻微` / `P5-建议`……（历史例：P2-5 demo 混合污染、P2-6 风险自查盲区）。
2. 修复：提交信息带编号（`fix: P2-5 xxx`）。
3. 回归：重跑 L1 + 相关路径测试。
4. 归档：CHANGELOG 对应版本段记一行 `- 修复 P2-5 …`。

## 4. 与现有工程门禁的衔接

| 已有设施 | 作用 | 本机制补什么 |
|---|---|---|
| `commitlint.config.js` | 提交信息规范 | 无（沿用） |
| `.github/workflows/ci.yml` | doctor + pytest 硬门禁 | 补「L2 未过不得合入」的约定 |
| `.github/PULL_REQUEST_TEMPLATE.md` | PR 自检项 | 补一条引用本 checklist 链接 |
| `.github/CODEOWNERS` | 路径默认审核人 | 🔴 级路径 owner 终审即它保证 |
| `CHANGELOG.md` | 版本变更记录 | P# 修复归档（已在用） |
| `.gitignore` | 私有边界 | 新增私有脚本必须同步登记（红线 2） |

**建议（可选落地，不阻塞本版）**：CI 增加「改动含 `core/` 或 `pipeline/*.py` 时自动贴 checklist 到 PR」的步骤，提醒作者走 L2。

## 5. 首次执行清单

1. [ ] 本文档 + `checklist.md` 入库，`.gitignore` 放开 `docs/code_review/` 白名单。
2. [ ] PR 模板补引用本流程的一行。
3. [ ] 存量待审事项登记 P#（若有）。
4. [ ] 交接给全栈开发时：CODEOWNERS 审核人改其账号，并让他先通读本文档再动代码。

## 6. 附：30 秒速记

- 提交前：`doctor --ci` + `pytest` 绿 + checklist 自检勾完。
- 审查时：五维（正确/安全/可维护/性能/测试）+ 五红线，结论带 🔴🟡💭 + 位置 + 为什么 + 怎么改。
- 红线五条：demo 不当数据跑 / 凭证不进公开仓 / 品牌锁不静默覆盖 / 账号先行主路不破坏 / 飞书主键不乱改。
- 有问题 → 记 P# → 修 → 回归 → 归档 CHANGELOG。
